# 開発ガイドライン

このリポジトリ・デモリポジトリの既存コード（`app.py`, `check_annotations.py`, `contact_frame_finder.py`等）から観察された、実際に守られている慣習をまとめる。フォーマッタ・linterは導入していないため、これらは強制されておらず目視で揃える。

## コーディング規約

- 言語はPython 3。フレームワーク固有の書き方（Gradio、Ultralytics）はそれぞれの公式ドキュメント・既存コードに合わせる
- 型ヒントは現状使っていない（`app.py`等、関数シグネチャに型注釈なし）。新規に大きく書き加える場合も既存に合わせて無理に追加しない
- 定数はモジュール冒頭に`UPPER_SNAKE_CASE`でまとめて定義し、値の根拠をコメントで残す（例: `app.py`の`MAX_FRAMES`, `MAX_UPLOAD_MB`）
- コメントは「なぜそうしているか」（非自明な制約・過去に踏んだ落とし穴）を書く。「何をしているか」は書かない（コード自体で読み取れるものは書かない）
- 自動フォーマッタ・linterは未導入。既存コードのスタイル（インデント4スペース、ダブルクォート文字列など）に目視で合わせる

## 命名規則

- 関数・変数: `snake_case`（例: `predict_image`, `check_annotations`）
- 定数: `UPPER_SNAKE_CASE`（例: `MAX_FRAMES`, `ASSUMED_SEC_PER_FRAME`）
- ノートブックファイル名: スペース区切りの英語（例: `making dataset.ipynb`）。既存の命名に合わせ、アンダースコアへの統一などは行わない
- ドキュメント・変更履歴ファイル: `docs/`内は`kebab-case.md`、`.steering/`内は`YYYYMMDD-作業タイトル.md`

## スタイリング規約

フロントエンドはGradioの標準コンポーネントをそのまま使用しており、独自のCSSフレームワーク（Tailwind等）は導入していない。見た目の調整はコンポーネントの引数（`height`など）で行う。

## テスト規約

自動テストスイートは存在しない。以下の方法で正しさを確認する。

- **アノテーションデータ**: `check_annotations.py`を実行し、bboxの範囲外はみ出し・bbox数・keypoints数の不整合がないか確認する
- **学習済みモデル**: Colab上でのファインチューニング実行結果（学習曲線、未知データに対する目視評価）で確認する。数値目標はREADMEに記録する
- **デモアプリ**: コード変更後、本番pushの前に`gradio.launch(share=True)`で一時的な公開URLを発行し、実データ（画像・動画）を使って実際に推論エンドポイントまで通して動作確認する（`gradio_client`から`api_name`を指定して直接叩く、または実際にブラウザから触る）。ローカルにモデル重み・依存関係一式を揃えた仮想環境を用意して検証する
- UIの見た目に関わる変更は、実際にブラウザ（できれば対象デバイス、例: 縦長画像の見え方ならスマホ/ノートPCの画面サイズ）で確認する

## Git規約

- コミットメッセージ: 短い英語の句、過去形、prefix（`feat:`等）は使わない（例: `added validation for annotation`, `modified limitation`）
- 1コミット1変更を基本とする。無関係な変更を1コミットにまとめない
- `volleyball_projects`と`pose_estimation_model_for_volleyball`は別リポジトリなので、それぞれ独立してコミット・pushする（同じ変更でも2箇所に分けてコミットする必要がある場合がある）
- デモリポジトリへのpushは、HFアカウントに登録されたSSH鍵を持つ環境からのみ可能（`CLAUDE.md`参照）
