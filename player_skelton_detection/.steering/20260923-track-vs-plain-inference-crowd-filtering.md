# 2026-09-23: `model.track()`と`model()`で観客の誤検出結果が異なる理由の調査、および動画タブへの導入見送り

## やったこと

ユーザーから「同じ`IMG_5224.MOV`の同じ箇所（2秒付近）で、HF Studio（デモアプリ）では観客の中に骨格が誤検出されるが、Google Colabで`model.track()`を使うと同じ箇所で誤検出されない」という報告があり、原因を調査した。あわせて、デモアプリの動画タブに`model.track()`を導入するかどうかを検討し、今回は見送ることにした。

## 原因（調査結果）

デモアプリ（`pose_estimation_model_for_volleyball/app.py`）の`predict_video`は、動画をフレームごとに独立して`model(frame)`（トラッキングなし）で処理している。一方、Colabでの検証は`model.track()`を使っていた。両者は**同じモデル重み**を使っているが、検出結果をどう選別するかの仕組みが異なる。

- `model()`（プレーン推論）: そのフレーム単体で confidence ≥ 0.25（Ultralyticsのpredictデフォルト）の検出をそのまま返す。時間的な文脈は一切考慮しない
- `model.track()`: 内部のトラッカー（インストール済みultralyticsのデフォルトは`tracktrack.yaml`）が、検出結果をそのまま返すのではなく「トラックとして採用するか」を判定してから返す。実際の閾値設定は以下の通り（`ultralytics/cfg/trackers/tracktrack.yaml`を確認）:
  - `track_high_thresh: 0.6` — 高信頼度とみなす閾値
  - `track_low_thresh: 0.25` — 既存トラックの継続にのみ使える低信頼度側の閾値（新規トラックの開始には使えない）
  - `new_track_thresh: 0.7` — **新規トラックを開始できる最低confidence**
  - `min_track_len: 3` — トラックとして確定するまでに必要な最小フレーム数

つまり`model.track()`では、confidence 0.25〜0.7の検出は「既存トラックの継続」にしか使えず、単独で新しい人物として登録されない。さらに3フレーム連続で追跡できて初めて出力に含まれる。観客席の誤検出は、1フレームだけ一時的にconfidence 0.25〜0.7程度で発生したものと考えられ、`new_track_thresh`未満、かつ3フレーム連続で再現しなかったため、トラッカーに「ノイズ」として除外されたと考えられる。

`ultralytics/trackers/track.py`の`on_predict_postprocess_end`で、`predictor.results[i]`が`tracker.update()`が返したトラック採用済みの検出のみで丸ごと置き換えられる実装になっており、トラック未採用の生検出は結果に含まれない。

なお`model.track()`は内部で検出器自体のconfidenceしきい値を0.1とデフォルトより低く設定する（`engine/model.py`の`track()`実装）。つまり「検出自体を見逃している」のではなく、「検出はしているが、トラッカーが採用を見送っている」というのが正確な理解。

## デモアプリへの`model.track()`導入を見送った理由

技術的には可能で、Colabで確認できた「観客の一時的な誤検出をフィルタする」効果は動画タブにも適用できるはずだが、以下の理由で今回は見送った。

1. **フレーム間引き（downsample）との相性問題**: `predict_video`は`MAX_FRAMES`を超える動画で間引きがONの場合、`stride`個おきにフレームを処理する（連続フレームではない）。`model.track()`は連続フレームでの動き予測を前提にしているため、大きく間引いた状態でトラッキングを使うと、以前`baselite_test.py`で見つかった不具合（[`.steering/20260922-baselite-test-tracking-bug-fix.md`](20260922-baselite-test-tracking-bug-fix.md)参照）と同様に、検出数が大幅に減ってしまう可能性が高い。導入する場合は`stride == 1`（間引きなし）の時だけトラッキングを使う、といった条件分岐が必要
2. **モデルがユーザー間で共有されている**: `model`はモジュールレベルのグローバルオブジェクトで全ユーザーが共有している。`model.track(persist=True)`はトラッカーの内部状態をこの`model`に保持し続けるため、何もせず切り替えると別のユーザー・別の動画のトラッキング状態が引き継がれてしまう懸念がある（`docs/architecture.md`に記載済みの既知の制約）。各`predict_video`呼び出しの最初でトラッカーをリセットする実装が必要
3. **トラック確定までの立ち上がりの遅れ**: `new_track_thresh`や`min_track_len: 3`により、本物の選手であっても最初の数フレームは検出結果に出てこない可能性がある。誤検出を消す代わりに、動画冒頭で本物の選手の検出が一瞬遅れる、というトレードオフが生じる
4. **フレーム選択機能（`predict_video_frame`）との整合性**: 「フレームを選んで選手ごとにダウンロード」機能は、選択したフレームを単独で再推論している（トラッキングなし）。動画本体をトラッキング有りにすると、「動画では消えていた誤検出が、フレーム選択で見ると復活する」といった見え方の不一致が起きうる
5. **JSONエクスポートへの`track_id`追加が必要になる**: トラッキングを導入するなら、当初の設計（`docs/functional-design.md`）通り、ダウンロードJSONにも`instance_id`だけでなく`track_id`を含めるのが自然な流れになり、スキーマ変更が付随する

## 結論・今後

今回はデモアプリの動画タブへの`model.track()`導入は見送り、現状（フレームごとに独立した`model()`呼び出し、トラッキングなし）を維持する。導入する場合は、上記1〜5を踏まえた設計・実装が必要。特に1（間引きとの相性）は既知の再発リスクがあるため、対応する場合は`stride`に応じてトラッキングの有無を切り替える実装を最初から組み込むこと。
