# プロダクト要求定義書

> **ドラフト**：`player_skelton_detection`プロジェクト開始にあたっての要求定義。内容は今後の議論で更新されうる。

## プロダクトビジョンと目的

試合動画を入力すると、コート上の選手の骨格（キーポイント）を検出できるシステムを開発する。

前身の`setter_skelton_detection`ではセッターのみに限定して骨格検出モデルをファインチューニングしたが、セッター1人だけを検出対象とする実用性の低さ（分析用途としての価値が限定的、汎用性に乏しい）が課題として残った。本プロジェクトはこの反省を踏まえ、対象をセッターに限定せず全選手に広げることで、より実用的で見せられるシステムを目指す。

本プロジェクトは著者本人の自己学習・ポートフォリオ（履歴書記載）としての側面を持つ。そのため「研究として面白いが結果が不確実なもの」より「実際に動き、見せられる成果物」を優先する方針は前身プロジェクトから引き継ぐ（`../../setter_skelton_detection/docs/product-requirements.md`参照）。

## ターゲットユーザーと課題・ニーズ

- **一次ユーザー: 開発者自身** — 機械学習・データセット構築・モデルデプロイの一連の経験を積み、成果物をポートフォリオとして提示したい。
- **二次ユーザー（将来的な想定）: バレーボールのコーチ・アナリスト** — 試合映像から選手の姿勢データを半自動で抽出し、分析に使いたい。セッター限定だった前身に比べ、全選手を対象とすることでこの層への価値提供の余地が広がる（現時点ではこの層に向けた機能開発は行っていない。デモは技術デモの位置づけ）。
- **課題**: 汎用の人物姿勢推定モデルが試合動画の複数選手（重なり・部分遮蔽・ジャンプ等の動的な姿勢を含む）に対してどこまで通用するかが未検証。

## 主要な機能一覧

1. 画像・動画から、映っている選手（複数人）の骨格（キーポイント）とbboxを検出する推論機能
2. Webデモ（Hugging Face Space、Gradio）による画像タブ・動画タブでの一般公開（既存Space `pose_estimation_model_for_volleyball` を転用）
3. 検出結果（選手ごとのキーポイント座標・bbox、`model.track()`によるフレーム間`track_id`付き）をCSV/JSON形式でダウンロードできる機能
4. アップロード時の誤操作防止（表示サイズ調整、ファイルサイズ上限）— 前身プロジェクトの実装を踏襲

**可視化方針の補足**: 予測結果の可視化（全選手のスケルトンを重畳表示した画像・動画）は、既存のGradio実装（`results[0].plot()`による全インスタンス描画）の延長で実現可能と判断し、この段階では別媒体（専用ダッシュボード等）は導入しない。座標データのダウンロード機能もGradio標準コンポーネント（`gr.File`）で対応する。将来、選手ごとの軌跡・関節角度分析などダッシュボード的な機能が必要になった場合は、別途検討する。

## 成功の定義

### モデル評価・ファインチューニング判断基準

- 事前学習済み`yolo26n-pose`をそのまま試合動画に適用した際の精度を、目視評価と定量指標（mAP50-95等）の両方で把握できていること
- 上記評価に基づき、ファインチューニングの要否を判断できていること（要と判断した場合は、前身と同様に未知データでの精度改善を確認する）

### デモ・ポートフォリオ基準

- デモが実際に一般公開され、複数選手の骨格が外部から動作確認できる状態であること
- 履歴書・ポートフォリオとして提示できる完成度であること

## ビジネス要件

商用要件はない。個人の自己学習プロジェクトであり、以下の制約の中で完結させる（前身プロジェクトから引き継ぎ）。

- 学習・評価: Google Colab（無料枠）
- 推論・デプロイ: Hugging Face Spaces（ZeroGPU、無料枠、1日あたりのGPU利用時間に上限あり）
- ライセンス: `ultralytics`がAGPL-3.0のため、本プロジェクト・デモともにAGPL-3.0で公開（`../../LICENSE`）

## ユーザーストーリー

- 開発者として、試合動画をアップロードすると自動で複数選手の骨格が検出されるデモを外部に見せられるようにしたい
- 開発者として、汎用モデルの精度をまず定量的に把握し、ファインチューニングにコストをかけるべきか判断したい
- デモの訪問者として、片側チームだけが映る動画・両チームが映る動画のどちらをアップロードしても、映っている選手の骨格が検出される結果を見たい
- デモの訪問者として、誤って長時間・大容量の動画をアップロードしてしまっても、アップロード完了を待たされずにエラーに気づきたい
- 開発者として、無料GPU枠を使い切らないよう、1回あたりの処理時間・動画の長さに妥当な上限を設けたい
- （将来的な）分析用途のユーザーとして、重畳表示された動画だけでなく、選手ごと（`track_id`単位）のキーポイント座標を生データとしてダウンロードし、他ツールで分析に使いたい（ただし`track_id`はブロック時の密集等でIDが入れ替わりうる、という限界を理解した上で利用する）

## 受け入れ条件

- 事前学習済み`yolo26n-pose`の評価: 試合動画から抽出したフレーム（目安20〜30枚。工数次第で段階的に縮小する場合あり。詳細は`../plan.md`「評価計画」参照）に対するmAP50-95等の定量指標、および目視でのスポットチェック結果をREADME/`.steering/`に記録していること
- ファインチューニングの要否判断: 上記評価結果を根拠とした意思決定が記録として残っていること
- Webデモ: 画像・動画の両タブが実際に複数選手の推論結果を返すこと。既存の誤操作防止機能（表示サイズ調整、アップロードサイズ上限）が維持されていること
- 座標データダウンロード: 画像・動画の両方で、検出結果（bbox・キーポイント座標。動画は`track_id`、画像は`instance_id`）を含むCSV/JSONファイルが実際にダウンロードできること
- ライセンス表記: デモ・GitHubリポジトリ双方にAGPL-3.0のソース公開リンクが機能していること

## 機能要件

- YOLO-pose（`yolo26n-pose`、まずは事前学習済みモデル。要否に応じてファインチューニング済みモデルに切り替え）による、単一クラス（`person`）での複数インスタンス（選手ごと）のbbox＋キーポイント検出
- 画像入力・動画入力の両方に対応した推論
- 動画は指定フレーム数を超える場合、間引き処理（downsample）または明示的なエラーで対応（前身の実装を踏襲）
- アップロードサイズ上限（`max_file_size`）による誤操作防止（前身の実装を踏襲）
- 検出対象は入力画像・動画に映っている選手全員とし、片側チームのみ／両チームが映る、といったカメラアングルの違いを問わない（審判・ベンチ・観客等、コート上でプレー中の選手以外は対象外とする方針を基本とするが、除外ロジックの要否は評価結果を見て判断する）
- 検出結果（選手ごとのbbox座標、17キーポイント座標と信頼度）をCSV/JSON形式でダウンロード可能にする。動画はフレームごと・`model.track()`による`track_id`付き、画像は単一フレームのため`track_id`を持たない検出順ID（`instance_id`）付きとする
- 動画推論には`model()`ではなく`model.track(persist=True)`を用い、フレームをまたいだ選手の`track_id`を付与する（IDの入れ替わりが起こりうることを既知の限界として許容する）

## 非機能要件

- Hugging Face ZeroGPUの1日あたりGPU利用枠（未ログイン2分/日、無料アカウント5分/日、Space横断で共有）を1回の利用で使い切らないよう、処理時間を制御する（前身の実装を踏襲）
- ローカル環境（GPU非搭載でも）で動作確認できること
- AGPL-3.0のソース公開要件を満たすこと（Spaceのソースコード・GitHubリポジトリともに公開）
- 評価の再現性: mAP等の定量評価に用いるデータセット・評価スクリプトは再実行可能な形（Colab notebook等）で残すこと
